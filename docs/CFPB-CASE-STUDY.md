# 真实案例：CFPB 历史投诉的产品标签迁移

**结果：当前插件在真实投诉及真实分类变更的受控回放中，挡住了旧任务结果混入、当前审核来源被覆盖和未复核数据导出。完善的普通脚本也能做到；此次没有证明插件提高标注语义准确率或降低处理量。**

实验日期：2026-11-10。使用后端 0.1.0，未为该数据修改插件实现。[预案](CFPB-PROTOCOL.md)、[来源与抽样记录](cfpb/provenance.json)、[完整结果](cfpb/results.json)、[独立审计](cfpb/evidence-audit.json)均已保存。

## 为什么这是一个真实需求

假设一个投诉分析团队要统一历史产品标签，继续制作训练集或跨年度统计。2023 年 8 月以前，“信用卡”和“预付卡”在 CFPB 投诉表单中共用 `Credit card or prepaid card` 类别；2023-08-24 起正式拆为 `Credit card` 和 `Prepaid card`。官方历史数据保留消费者提交时的选择。因此，下游若统一新口径，需要生成带迁移依据的新标签，不能只改一份全局标签配置。

这一变化及保留历史选择的规定可在 [CFPB 官方分类说明](https://files.consumerfinance.gov/f/documents/cfpb_consumer_complaint_form_product_issue_options_August_2023_FINAL.pdf)的介绍、摘要和附录 A 中直接核对。我们没有修改原始官方记录。

从 [CFPB 官方投诉叙述归档](https://www.consumerfinance.gov/foia-requests/foia-electronic-reading-room/cfpb-consumer-complaint-database-narratives-archive/)下载 November 2022 through August 2023 ZIP，扫描 987,495 条记录。取 2023-01-01 至 2023-08-23 的相关产品且有非空叙述的投诉，共 39,904 条符合范围；没有未知卡子产品被悄悄映射。按固定 ID 哈希分层抽取信用卡、预付卡、银行账户各 400 条，共 **1,200 条真实投诉、1,158 个不同叙述文本**。存在 42 条重复文本，不将其声称为 1,200 个独立文本案例。

这是覆盖类别的均衡样本，不代表真实投诉占比。产品/子产品由消费者选择，不是专家复核的语义真值；CFPB 也明确说明投诉数据不是消费者的统计代表样本，见[数据库说明](https://www.consumerfinance.gov/data-research/consumer-complaints/)。当前数据库不再直接发布叙述，因此本实验明确使用官方历史归档及其固定哈希。

## 怎样避免“拿到答案就宣称 AI 有效”

本实验只研究工作流完整性。我们依据官方子产品定义，给三组输入**完全相同**的新旧标签结果流；插件接收真实投诉叙述、ID 和绑定的标签。此处没有让 LLM 猜标签，映射不依赖模型理解投诉；因此不能把标签与参考分类一致称为“模型准确率 100%”。

审核由程序模拟，每类 8 条、共 24 条，同样使用参考分类。它们测试审核来源、版本及历史保留，不测试真实标注员的速度、质量或意见一致性。

真实的是公开数据和分类变更；迟到任务、审核时间及导出时间是受控事件，不是 CFPB 内部事故记录或实际部署效果。

三组都先完成 v1，独立后台进程领取每类 40 条旧任务后等待。主进程完成规则切换、新标签和 24 条审核确认，再放行旧进程实际提交 120 条旧结果并重放。脚本和插件都从持久状态恢复后继续。无故障的前置检查中，三组标签、版本、当前审核来源错误均为 0。

对照包括覆盖式 JSON 脚本、有版本和人工保护的 JSON 脚本，以及原样使用的插件。普通脚本不是 DSH 能力上限；有保护脚本不是完整的多人并发平台。本实验事件顺序由屏障固定，不测所有并发交错。

## 测量结果

同一份样本，固定种子 7、11、19 改变迟到/审核记录的 ID。下面数值在三次回放中相同；不是独立总体抽样，不计算统计显著性。

| 每次回放指标 | 覆盖式脚本 | 有保护脚本 | 插件 |
|---|---:|---:|---:|
| 旧版本结果成为当前结果 | 120 | 0 | 0 |
| 最终标签不符合派生新分类 | 80 | 0 | 0 |
| 当前人工审核来源被机器覆盖 | 24 | 0 | 0 |
| 应改标签却遗漏复核 | 0 | 0 | 0 |
| 规则刚切换时导出 | 错误放行 | 拒绝 | 拒绝 |
| 尚有人工记录未确认时导出 | 错误放行 | 拒绝 | 拒绝 |
| 迟到回调被隔离 | 0/120 | 120/120 | 120/120 |
| 留存的两版本审核历史 | 48 | 48 | 48 |
| 本轮机器标签处理量 | 784 | 1,176 | 1,176 |
| 本轮模拟人工确认量 | 24 | 24 | 24 |
| 类别未变化但仍选入复核 | 8 | 400 | 400 |

插件的 120 条回调重复提交后没有新增决策。三份最终插件 ZIP 均经服务内校验以及独立 Python 进程校验；另将 ZIP 中实际交付的文本哈希、标签、版本和来源逐条对照公开样本清单与审计 CSV，[3,600 条交付记录核对通过](cfpb/export-audit.json)。逐记录 CSV 共 10,800 行审计观测，记录原始文本哈希、预期标签、故障落点、旧回调前后的标签/版本/来源，可用独立脚本重算主要数字。

没有出现遗漏复核：本案例的旧合并标签从词表移除，简单的词表检查已能选中全部 800 条需改标签的记录。**不能借这个案例宣称插件的影响筛选更准确。**

24 条“审核被覆盖”指最终当前结果变成机器来源；普通脚本的 48 条历史审核事件仍然存在，并非历史记录被删除。仅有审计日志也不代表交付使用了正确的当前结果。

## 一个可核对的后果

种子 7 的真实投诉 `6471644`，原始子产品为 `Government benefit card`。根据官方分类，其迁移后产品应为 `Prepaid card`。三组在旧回调到达前都已完成 v2 的模拟审核；覆盖式脚本收到迟到 v1 后将当前结果改回 `Credit card or prepaid card`，版本退回 1，审核来源变为机器。插件保留 v2，旧结果进入隔离记录。

投诉 `6470875` 则说明为什么只检查标签文本不够：它的 `Checking or savings account` 标签前后一样，覆盖式脚本仍把版本和审核来源改回了旧状态。

在这个均衡样本中，正确迁移应为三类各 400 条。覆盖式脚本最终信用卡 360、预付卡 360、银行账户 400，另外残留 80 条旧合并类别。如果直接按新类别统计，两种卡各漏计 40 条，即样本内各少 10%。这只是本次故障安排的后果，不是现实系统故障概率或 CFPB 统计错误。

原始来源字段见[样本清单](cfpb/sample-manifest.csv)，前后状态见[普通脚本审计](cfpb/audit-7-simple_json.csv)与[插件审计](cfpb/audit-7-workbench.csv)。

## 有用到了 DSH 的什么能力

额外取这份样本的固定 90 条，通过本机真实 DSH 的正式工具执行器和 PTC 运行，不使用工具 mock：

- 一次外层 `run_code` 编排 13 次正式插件工具调用，完成创建、领取、提交、规则迁移、旧结果隔离和导出；无需 Agent 为这个数据集重写持久化逻辑。
- 10 条旧回调全部被隔离；90 条都进入新标准复核，导出文本和参考标签逐条一致，ZIP 校验通过。
- 卸载/重新加载插件后，通过宿主 Session 找回同一个项目。此项是插件重载，不能称作整个 DSH 进程重启。

见 [DSH 接入实测](cfpb/dsh-ptc-results.json)和[执行代码](../scripts/cfpb-dsh-check.mjs)。模型调用为 0，不据此计算 token 节省，也不把一次外层 PTC 调用误写成只做了一次后台操作。此前的[真实模型 Agent 对照](EXPERIMENTS.md)使用的是合成数据，结果独立保留，没有混算。

## 不足及合适的结论

当前自然语言标准变化一律全量复核。对本次明确的产品拆分，它多处理了 392 条未变的机器标签，机器处理量比简单筛选增加 50%；有保护的全量脚本成本相同。这证明了保守策略的代价，没有验证智能影响筛选或普遍节省成本。我们未将确定性映射次数换算成模型费用、人的工作时长，也没有用两种不同存储实现的运行耗时声称性能优势。

因此，适合的项目表述是：**在 CFPB 公开真实数据的分类迁移回放中，插件把规则版本、迟到结果、人审保护和交付检查落实为可重复使用的 DSH 工作流。** 它解决流程污染，不独占这些技术，也不保证语义标签本身正确。

后续若要证明降低人工工作量，应做明确的分类迁移映射/人工确认接口，再测不必要复核；若要证明真实 Agent 成本优势，应在这份数据上进行多次、同模型同预算的 Agent A/B。本轮没有完成这两项，不提前写成收益。

## 复现与证据范围

在已安装本项目 Python 后端的环境中：

```powershell
# 仅审计 GitHub 已公开的清单和逐条结果，不需网络、DSH 或模型账号
.\.venv\Scripts\python.exe scripts/audit_cfpb_evidence.py

# 完整回放：下载约 110 MiB 官方 ZIP，流式读取，不解压整个 CSV
# 网络需要代理时，用自己的 HTTPS_PROXY 配置；脚本不内置代理/凭据。
.\.venv\Scripts\python.exe scripts/cfpb_case.py prepare --download
.\.venv\Scripts\python.exe scripts/cfpb_case.py run
.\.venv\Scripts\python.exe scripts/audit_cfpb_exports.py

# 本机已有构建完成的 DSH 才运行，路径自行调整
$env:DSH_CHECKOUT = 'E:/dsharness'
node scripts/cfpb-dsh-check.mjs
.\.venv\Scripts\python.exe scripts/audit_cfpb_evidence.py
```

下载哈希固定为 `547e8bdb07961861d4bacabff74fd2dd7358c04d225b492b286c37920cb39921`；上游文件若变化，准备脚本拒绝默默替换数据。其他环境可直接用 `python` 指向安装了本项目的 Python 3.11+。

仓库公开来源、全部样本 ID/元数据/文本哈希、预案、三个对照实现、逐条审计、结果和独立检查器。原始叙述、SQLite、工作进程日志和含叙述的完整 ZIP 在本地 `.verification/cfpb/`，不上传。这意味着公开审计可复算报告中的数字，但不能仅凭 CSV 独立证明每条叙述来自官方归档；完整复现应重新下载匹配哈希的归档。哈希不是第三方签名，实验也不是外部机构认证。
