# 真实 DSH 小试预案

在首次模型调用前写入。24 条来自固定模板的客服文本，完整可执行规则，2 条预置的模拟人工审核，24 条延迟 v1 回调。不是盲测，也不研究人工实际效率。

两组各一次独立 DSH Session：A 用普通 Python/JSON 编写可靠流程（明确允许保护逻辑，不限定弱实现）；B 用工作台。均给出相同旧规则、新规则、原文本、旧状态和操作目标。B 的预置后台状态与 A 的 JSON 对齐。主模型 deepseek-official/deepseek-flash，low；每轮 600 秒，上限 8192 output tokens/次模型调用。实际 token/calls 另记；没有预算配平。

第一轮改规则、处理机器可完成的项目、隔离旧回调，保留两条人工记录待复核，禁止假造人工批准或完整导出。第二轮用同一 Session ID 在新 DSH 进程恢复、再次处理相同旧回调，交付恢复报告。预期不会生成最终完整数据集，因为人审未完成；正确阻断是成功行为。

独立审计 24 条记录的标签/版本/待审标记、两条人审保留、未放行导出和持久交接文件。B 再直接核验 SQLite 状态，A 核验 JSON 交付。保存工具调用次数、工具错误、provider usage 和墙钟。两组存储方式不同；结果不可证明普遍生产力或标注质量提升。如两组均完成，则只报告可靠流程的可用性及本次成本，不宣称插件更会推理。
